# Manthan Glossary

> 15 terms, every one with a Swiggy example.
> Read this before the workshop. Reference during. Keep after.

---

| Term | What it is | Why it matters | Swiggy example |
|---|---|---|---|
| **JTBD** (Jobs-To-Be-Done) | Defines users by the job they hire the product for, in a specific situation — not by demographics. | Demographics don't predict behavior; situations do. A 22-year-old and a 42-year-old "hire" Swiggy for the same job when they share the same trigger. | "When I'm working late and don't want to think about food, I want something hot in 30 minutes from a place I trust, so I can keep working without a decision tax." |
| **Archetype** | A behavioral pattern of a user type, drawn from research, named for memorability. | Personas are demographic decoration. Archetypes are decision tools — they tell you who to design for and who to ignore. | "The Late-Night Coder" (orders 10 pm+, repeats same 3 places, hates discovery) vs. "The Weekend Curator" (orders Fri-Sun, browses cuisines, tries new places monthly). Different products inside one app. |
| **Core loop** | The repeated user action that creates value and brings them back. | For any retention product, the loop *is* the product. If the loop isn't crisp, no marketing fixes it. | Open Swiggy → reorder favourite (1 tap) → track delivery → eat → rate → return tomorrow. The "1-tap reorder" is the loop's compression — every friction kills retention. |
| **MVP proof** | One sentence stating exactly what behavior the v1 is proving. | Without it, "MVP" becomes "everything we cut." | "We are proving that hungry users will reorder from one tap if delivery is fast and food arrives hot." |
| **Pareto** | The 5-criteria test that decides what ships in v1. A feature is in v1 only if it passes at least one criterion. | If everything is v1, nothing is v1. Pareto produces unambiguous yes/no decisions. | Cut "personalised cuisine recommendations" from v1 if "search + reorder" alone validates the bet. Defer the recommender until you have data. |
| **Trigger to revisit** | A measurable event that means "now build the deferred feature." | Without triggers, the priority queue becomes a graveyard. | "If 30%+ users repeat the same restaurant in week 1, build the 'reorder favourites' feature." Specific. Measurable. Auto-fires. |
| **Reference brief** | One sentence anchoring how the product should feel, by reference to a known product. | AI build tools default to generic SaaS without direction. One sentence eliminates the default. | "Feels like Amazon's logistical reliability, for hungry people in a hurry — not like a foodie magazine." Tells the prototype to optimise for confidence + speed, not exploration. |
| **AI surface** | A specific user-facing moment in the product that is powered by an AI model. | Each AI surface is its own micro-product with its own prompt, its own quality bar, its own failure modes. | Swiggy's AI surfaces: recommendation feed (predicts what you'll order), search re-ranker (matches "biryani" to nearby quality), support chatbot (handles "where's my order"), price-surge explainer. Four AIs, four products. |
| **5-lens review** | A scorecard applied to any prototype: Product / Emotion / UX / Visual / System. | Catches what a single review lens misses. | After building a Swiggy "late-night cravings" prototype: Product (does it cut decision time?) Emotion (does it feel like a friend?) UX (is order in 3 taps?) Visual (does it feel premium for 2 am?) System (can it scale to 100 cities?). |
| **Parallel agents** | Spawning multiple Claude Code sub-agents that work simultaneously on independent tasks, then converge. | When the work decomposes into independent streams, parallelism cuts wall-clock time without losing rigor. | Research blitz: agent A pulls Reddit complaints about food delivery, agent B scans Zomato/Eatsure menus, agent C analyses weather-driven order patterns. All three run at once and report back. |
| **Sub-agent** | A specialised Claude Code agent with a focused role, tool access, and persona. | Generic agents drift; specialised agents stay sharp. | A "cuisine-trend researcher" sub-agent that only reads food-trend reports and food-blogger newsletters, vs. a generic "researcher" that does everything badly. |
| **Project memory** | A persistent file (`CLAUDE.md`) Claude Code reads at session start. Encodes context, rules, and preferences. | Without it, every session re-discovers context. With it, the team's institutional knowledge travels. | Swiggy team's `CLAUDE.md` could encode: "We never push deals to Tier-2 cities during festivals" — so any future feature build automatically respects that rule. |
| **Vibe coding** | Building a working prototype quickly using AI-generated code, often in a single file, optimised for speed of iteration. | The opposite of vibe coding is over-engineering. v1 prototypes don't need a database; they need a working flow. | Building a quick "Late Night Cravings" tab as a single HTML file with mock restaurant data, no backend, no auth — just enough to validate the flow with a real user. |
| **Single-file HTML** | A complete prototype in one `.html` file with inline CSS and JS. Opens in any browser. No build step, no server, no dependencies. | Removes every barrier between thinking and showing. The prototype runs the moment it's written. | The "Late Night Cravings" prototype is `late-night.html` — open it in Chrome, click around, ship the link to 3 PMs for feedback in an hour. |
| **Mock data** | Fake but realistic data hard-coded into the prototype, replacing real APIs. | Real data systems take weeks to wire up. Mock data unblocks design and flow testing in minutes. | A `restaurants.js` array with 5 fake restaurants instead of Swiggy's 250,000 real ones. Enough to demo the flow without touching a backend. |
